# 진행 순서·일정·완료 조건

180분 안에 P0를 실제 시연하는 것이 우선이다. P1 예측·사진은 설계를 완료한 추가 범위이며 시간 조건을 충족하면 구현한다. 아래 체크는 실제 구현 후에만 완료로 바꾼다.

## 작업 방식

맥북 1대, 작업 폴더 1개, 개발 서버 1개에서 함께 진행한다. 팀원 A/B 구분이나 파일별 담당을 두지 않는다. 역할별 브랜치를 만들거나 별도 구현 결과를 주고받는 과정도 두지 않는다.

각 기능의 데이터·API·화면을 한 흐름으로 구현하고 동작을 확인한 뒤 다음 단계로 넘어간다. 공통 타입·패키지·환경 설정도 같은 작업 폴더에서 관리한다. 기능이 연결될 때마다 작은 커밋으로 기록하고, 계약이 달라지면 해당 스펙도 함께 수정한다.

사용자 구분은 같은 맥북의 서로 다른 브라우저 프로필 또는 일반 창·시크릿 창으로 검증한다. 같은 프로필의 탭 두 개는 localStorage를 공유하므로 서로 다른 사용자로 세지 않는다. 관리자 화면은 별도 탭에 열어 시연한다.

## 작업별 산출물

| 순서 | 구현 범위 | 인수 조건 |
| --- | --- | --- |
| T01 초기화·계약 | 프로젝트·공통 타입·환경 변수·DB 스키마 | dev 실행, 타입·시드 ID 확정 |
| T02 시설 조회 | 시드·조회 API·시설 목록·상세·QR | 실제 DB로 시설·고장·빈 화면 표시 |
| T03 신고·참여 | 저장 API·익명 ID·신고 폼·참여 UI | 요청 재시도·고유 참여·원본 보존 |
| T04 AI 판별 | 중복 판별 어댑터·저장 연결·결과 안내 | 동일/다른 고장, 타임아웃 fallback |
| T05 관리자 | 조회·수정 API·목록·상세·편집 UI | 정렬·상태 전이·ETA·해결 시각 반영 |
| T06 P0 연결 확인 | 사용자부터 관리자까지 전체 흐름 | 신고 → 관리자 처리 → 사용자 재조회 |
| T07 예측 | 계산 함수·API·카드·근거 표시 | 데모 7/2/null, 주의도·데이터 부족 표시 |
| T08 사진 | 입력·검증·저장·조회 | 유효 파일 표시, 잘못된 파일 거절 |
| T09 시연 준비 | 핵심 흐름 확인·필요한 결함 수정·발표 준비 | 아래 최소 완료 조건 충족 |

T07·T08은 T06 완료 후 남은 시간에 순서대로 진행하며, 시간 관문을 넘기면 T09로 이동한다.

## 180분 일정

| 시간 | 진행할 작업 | 관문 |
| --- | --- | --- |
| 0–15분 | T01: 프로젝트·타입·DB 뼈대, AI 키·모델 확인 | 개발 서버 실행 |
| 15–40분 | T02: 시드·시설 조회 API·상세 화면·QR | 실제 시설 상태 조회 |
| 40–75분 | T03: 신고·참여 API와 폼, 중복 클릭·재전송 처리 | AI 없이 접수·참여 가능 |
| 75–100분 | T04: AI 판별 연결, 병합·별도 접수·오류 안내 | 같은 고장 병합·다른 고장 분리 |
| 100–125분 | T05–T06: 관리자 API·화면, 전체 흐름 확인 | P0 통합 완료 |
| 125–145분 | T07: 예측 계산·API·카드, 여유 시 T08 사진 | P1 완료 기능만 켬 |
| 145–155분 | T09: 핵심 흐름 한 번 확인, 발견된 문제만 수정 | 시연을 막는 문제 해결 |
| 155–180분 | 미완료 기능 정리, 시드·브라우저 프로필 준비, 발표 구성 | 기능 추가 중단, 3분 시연 |

125분에 P0가 미완료면 125–145분도 P0 통합에 사용하고 P1은 끈다. P1 중에는 예측을 먼저 구현한다. 사진·시각적 장식·추가 차트부터 줄이고 핵심 흐름을 한 번 확인할 시간만 확보한다.

AI 키·서비스에 문제가 있으면 명시적 mock으로 시연할 수 있지만 F04 실제 AI는 미완료로 기록한다. 기본 시연은 맥북의 브라우저로 진행한다. 별도 휴대폰으로 QR 접속을 확인하지 않았다면 모바일 실제 접속은 미검증으로 기록한다.

## 최소 완료 조건

아래 흐름을 한 번 확인한다. 이미 확인한 항목은 관련 동작이 바뀌거나 문제가 발견된 경우에만 다시 확인한다.

- [ ] 시설 조회 → 신고 → 다른 사용자 참여가 연결되고, 반복 참여로 인원이 늘지 않는다.
- [ ] 같은 문제는 병합되고 다른 문제는 별도 접수된다.
- [ ] 관리자 상태·예상 처리 변경이 사용자 화면에 반영된다.
- [ ] P1 예측을 구현했다면 실제 집계값과 데이터 부족 표시가 보인다.
- [ ] P1 사진을 구현했다면 첨부한 사진이 관리자 화면에 보인다.

## QA·테스트 원칙

구현과 시연에 필요한 최소 확인만 수행한다. 별도 QA 단계 확대, 전수 경계값 검사, 테스트 코드 추가, 같은 시나리오 반복 실행은 기본 작업에 포함하지 않는다. 타입 검사·lint·build·전체 테스트를 일괄 실행하는 완료 조건도 두지 않는다.

문서 변경은 변경 내용을 읽어 확인하는 것으로 마무리한다. 코드 변경은 영향을 받는 기능만 확인하고, 구체적인 오류나 데이터 손실 가능성을 해결해야 할 때에만 관련 검사를 추가한다. 통과한 검사를 관련 변경 없이 다시 실행하지 않는다.

입력 검사·파일 형식 확인·DB 제약·AI 결과 확인은 앱의 실제 동작 규칙이므로 구현에 유지한다. 동작 예시와 경계 조건은 스펙으로 참고하되 모두 자동 테스트로 작성할 의무는 없다.

## 3분 시연

1. **0:00–0:20:** 같은 고장 신고가 흩어지는 문제를 소개한다.
2. **0:20–0:45:** 프린터 QR 접속, 새 사용자 참여로 8명 → 9명을 보여준다.
3. **0:45–1:20:** 다른 브라우저에서 같은 증상을 다른 문장으로 신고해 기존 고장에 병합, 10명을 보여준다.
4. **1:20–1:45:** 용지함 파손을 신고해 다른 고장으로 분리되는 것을 보여준다.
5. **1:45–2:20:** 관리자에서 프린터를 처리 중·오늘 18:00으로 변경하고 사용자 화면을 새로고침한다.
6. **2:20–3:00:** P1이 완료됐다면 예방 점검 카드의 7건 예상·높음·계산 근거와 정수기의 데이터 부족을 보여준다. 미완료면 해당 시간에 처리 상태·중복 방지 구조와 확장 설계를 설명한다.

오늘 시연 중 추가한 신고는 다음 날 예측 기준부터 집계된다. 예측 숫자가 버튼 클릭 즉시 바뀌는 연출을 하지 않는다. 시연 전 synthetic 시드를 초기화하고 2개 브라우저 프로필·실제 AI 모드를 확인한다.
