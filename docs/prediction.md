# 고장·신고 예측 명세

P1 추가 기능. 관리자의 예방 점검 판단을 돕는 **신고량 예상 + 반복 고장 주의도**를 제공한다. 현재 고장 처리 목록과 별개이며, 점검 참고 지표가 실제 고장 확률을 의미하지 않는다.

## 질문과 결과

| 질문 | 첫 버전의 답 | 사용 행동 |
| --- | --- | --- |
| 다음 주 신고가 얼마나 들어올까? | 최근 4주 평균을 다음 7일로 외삽 | 점검·응대 업무량 참고 |
| 어느 시설을 미리 확인할까? | 최근 30일 신규 고장 건수에 따른 주의도 | 반복 발생 시설 예방 점검 |
| 정확히 언제 고장 날까? | P1에서는 제공하지 않음 | 실제 정비·센서 이력 수집 후 검토 |

이는 제품 설계용 휴리스틱이다. 통계적으로 검증된 고장 예측 모델이나 특정 성능을 주장하지 않는다. 학습 서버·벡터 DB·스케줄러·LLM 호출은 없다.

## 날짜와 관측기간

T는 **오늘의 Asia/Seoul 00:00**이다. 미래 7일은 [T, T+7일), 과거 28일은 [T−28일, T), 과거 30일은 [T−30일, T)이다. 구간 시작은 포함하고 끝은 제외한다.

현재 진행 중인 오늘의 신고는 평균과 반복 이력에 포함하지 않는다. 오늘 들어온 신고는 다음 날짜부터 반영된다. 현재 미해결 고장 수는 예외로 응답 생성 시점의 값이며 예측 데이터와 구분한다.

관측 시작은 Facility.observedFrom을 **다음 KST 자정으로 올림**한 날 O다. 이미 자정이면 그대로다. `observedDays = max(0, T와 O 사이의 완전한 일수)`다. 최초 신고가 없어도 수집이 정상적으로 진행된 날은 관측일이다.

예: 9월 1일 15시에 수집을 시작하면 9월 2일 00:00부터 완전한 하루를 센다. 테스트는 외부 시계를 읽지 않고 T를 함수 인자로 주입한다.

## 예상 신고량

1. 최근 28일 Report를 Issue의 facilityId로 묶는다.
2. 같은 `(facilityId, KST 날짜, clientId)`는 한 번만 센다. 같은 날 서로 다른 고장에 신고해도 시설 업무량 지표에서는 한 번이다.
3. 오래된 구간부터 7일씩 `weeklyCounts=[W1,W2,W3,W4]`를 만든다.
4. `N = W1 + W2 + W3 + W4`로 두고 `expectedReports7d = Math.round((N / 4) * 10) / 10`으로 소수점 1자리까지 반올림한다. 값은 음수가 될 수 없다.

프론트 표시는 `약 {값}건`이며 정수인 경우 불필요한 `.0`을 생략한다. 범위·신뢰구간·확률을 만들지 않는다. 사용자는 근거 `지난 4주 {N}건 ÷ 4`와 주별 건수를 펼쳐 볼 수 있다.

| 조건 | 반환 |
| --- | --- |
| observedDays < 28 | insufficient_data, 예상·주별 건수·28일 합계 모두 null, OBSERVATION_TOO_SHORT |
| observedDays ≥ 28, N = 0 | ready, 예상 0, 주별 0, OK. `최근 4주 신고 없음` 표시 |
| observedDays ≥ 28, 1 ≤ N < 4 | insufficient_data, 예상 null, 실제 주별 건수·합계는 반환, TOO_FEW_REPORTS |
| observedDays ≥ 28, N ≥ 4 | ready, N/4 반올림, OK |

0은 완전히 관측된 기간의 실제 무신고이며 데이터 부족과 다르다. 1–3건의 희소 이력에는 수치 예측을 보류한다. 최소 4건이라는 기준도 데모용 정책이며 검증된 통계적 기준이 아니다.

참여 버튼 클릭은 Report가 아니므로 예상 신고량에 포함하지 않는다. 원본 Report가 기존 Issue에 병합돼도 남아 있으므로 새로운 사용자의 신고는 수요에 반영된다. 동일 요청 재시도와 동일 사용자의 당일 중복 신고는 부풀리지 않는다.

## 반복 고장 주의도

관측일이 30일 이상이면 [T−30일, T)에 생성된 **Issue 개수** K를 센다. 해결·미해결 모두 포함한다. 재발하여 새 Issue가 생긴 경우는 별도 1건이며 같은 Issue에 병합된 Report 20개는 1건이다.

| 조건 | level | 표시·제안 |
| --- | --- | --- |
| observedDays < 30 | null | `데이터 부족 — 관측 30일 필요` |
| K = 0 또는 1 | low | `낮음 — 최근 반복 이력이 적습니다` |
| K = 2 | medium | `보통 — 최근 반복 이력을 확인해 주세요` |
| K ≥ 3 | high | `높음 — 예방 점검을 권장합니다` |

같은 시설에서 다른 부품이 고장 나도 시설 단위 K에는 포함한다. 따라서 UI는 `동일 고장 재발 확률`이라고 부르지 않는다. 관측 부족이면 issueCount30d도 null, 충분하면 실제 K를 반환한다.

예측 영역은 high → medium → low → 데이터 부족 순, 같은 주의도에서는 expectedReports7d 내림차순(null은 마지막) → facility.id 오름차순으로 정렬한다. 현재 수리 목록의 영향 인원 정렬은 그대로 둔다.

## 화면·API

카드에는 시설명, 주의도, 최근 30일 신규 고장 수, 현재 미해결 수, 예상 신고량, 근거, 관측일수를 넣는다. 상단에 기준일·갱신 버튼을 표시한다. 합성 데이터면 `데모 데이터 기반`을 눈에 띄게 표시한다.

예측과 주의도는 각각 데이터 충족 여부를 판단한다. 28–29일 관측이면 신고 예상은 나올 수 있어도 주의도는 데이터 부족이다. 둘 중 하나의 null로 카드 전체를 0으로 채우지 않는다.

API와 필드·상태 코드는 [api.md](api.md)를 따른다. 현재 MVP는 FEATURE_PREDICTIONS=true로 실행한다. 실제 데이터에서 계산하며 화면에 고정 예측 숫자를 넣지 않는다.

## 계산 예시와 경계 검증

| 관측일수 | 주별 신고 | 최근 30일 Issue | 예상 신고 | 주의도 |
| --- | --- | --- | --- | --- |
| 60 | 4, 6, 8, 10 | 3 | 7 | high |
| 60 | 2, 2, 2, 2 | 2 | 2 | medium |
| 10 | 불완전 | 불완전 | null | null |
| 28 | 1, 1, 1, 2 | 불완전 | 1.3 | null |
| 30 | 0, 0, 0, 0 | 0 | 0 | low |
| 30 | 0, 0, 0, 3 | 1 | null | low |

- T 직전 신고는 마지막 주에 포함, T와 정확히 같은 시각의 신고는 제외한다.
- T−28일과 정확히 같은 시각의 신고는 첫 주에 포함한다.
- 같은 날짜·clientId의 Report 10개는 1건, 다른 날짜나 다른 clientId는 각각 센다.
- 같은 clientId라도 다른 시설이면 독립적으로 센다.
- 한 Issue에 10명이 신고해도 반복 고장 K는 1이다.
- 최근 30일에 생성된 Issue가 해결되어도 K는 감소하지 않는다.
- 기간 이전에 열린 장기 미해결 Issue는 현재 수리 목록에는 나오지만 K에는 포함하지 않는다.
- 미래 시각의 기록은 어떤 과거 집계에도 포함하지 않는다.

## 후속 실제 예측 모델 · P2

정비 담당자가 확인한 실제 고장 발생·해결 시각, 오신고 여부, 정비·부품 교체, 설치 연식, 사용량·운영 시간, 관측 공백을 수집한다. 신고량과 물리적 고장은 서로 다른 목표값이다.

- 신고 예측 목표: 시설별 향후 7일 중복 제거 신고 수. 평가는 MAE와 최근 4주 평균 기준선 비교.
- 실제 고장 예측 목표: 판단 시점에 정상 운영 중인 시설의 향후 7일 내 확인된 고장 발생 여부. 이미 고장 난 시설은 정상 시설 예측 대상에서 제외.
- 시점 이후 해결 정보 등 미래 데이터를 입력에 넣지 않는다. 시간순 학습·검증과 시설별 분리를 검토한다.
- 실패 예측은 정밀도·재현율, 확률 보정, 실제 고장까지 확보한 선행 시간을 평가한다. 표본이 없으면 정확도를 보고하지 않는다.
- 충분한 실제 이력으로 단순 기준선보다 나은 결과를 확인한 뒤 확률 표시를 검토한다. 그전에는 현재의 이력 기반 점검 지표를 유지한다.

AI 오병합·분리 실패, 익명 ID 변경, 미신고 고장, 사용량·계절 변화는 모두 지표를 왜곡할 수 있다. 합성 시드로는 동작만 검증하고 예측 성능은 검증하지 않는다.
