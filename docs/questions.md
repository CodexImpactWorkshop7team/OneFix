# 행정 요청 MVP

## 용어와 범위

상위 개념은 **요청**, 유형은 **시설 요청 / 행정 요청**이다. ‘민원’이라는 표현의 무게를 줄이고 학교·회사·기관에서 공통으로 쓴다. 시설 요청은 처리 상태, 행정 요청은 공통 답변을 결과로 제공한다. 원문 접수 건수와 참여 인원은 구분한다.

한 워크스페이스에 한 캠퍼스 또는 기관을 전제로 한다. 담당 부서는 학사·수업, 장학·등록, 사무국·생활행정 3개다. 적용 시기는 작성자가 학기·월 등으로 명시한다. 부서 코드와 적용 시기 문자열이 같은 요청끼리만 병합한다. 시기 표기가 다르면 별도 접수된다.

## 사용자 흐름

1. 행정 요청 게시판에서 제목·내용·적용 시기·답변을 검색한다. 부서와 답변 상태로 필터링할 수 있다.
2. 같은 요청이 있으면 ‘나도 궁금해요’로 참여한다. 없으면 제목(5–120자), 내용(5–1,500자), 부서, 적용 시기(1–40자)를 입력한다.
3. 서버가 같은 부서·시기의 최근 30개 대표 요청과 비교한다. 같은 답변으로 해결 가능할 때만 취합하고 원문을 보존한다.
4. 신규 또는 취합 결과와 대표 요청을 표시한다. 이미 답변이 있으면 즉시 볼 수 있다.
5. 대표 요청의 `?id=` 링크로 다시 방문한다. 새로고침으로 답변을 확인한다.

랭킹은 브라우저별 참여 인원 내림차순, 동률이면 최초 접수 시각 오름차순, 마지막으로 ID 순이다. 원문을 여러 번 접수해도 같은 브라우저는 한 명이다. 필터 결과 안에서 순위를 표시한다. 답변 완료 요청도 참여·검색할 수 있다.

## 담당자 흐름

행정 요청 관리 화면은 전체 목록을 기본으로 보여준다. 공통 안내 유무와 원문별 답변 상태는 별도로 표시한다. 대표 요청을 열면 취합 원문을 확인하고 5–5,000자 공통 답변을 게시한다. 답변은 대표 요청에 저장하여 모든 참여자와 원문에 공통 적용한다. 기존 답변을 수정할 수 있고 다른 저장과 충돌하면 새로고침하도록 안내한다. 답변 시각과 담당 부서가 함께 표시된다.

중복 판별 AI는 대표 요청 ID 또는 null만 반환한다. 주제만 비슷하거나 기간·제도·자격·개인 상황이 다르면 합치지 않는다. API 실패/시간 초과 시 별도 접수하고 사용자에게 안내한다. mock 모드에서는 제목과 내용의 공백을 정규화한 완전 일치만 취합한다. 규칙으로 확인 가능한 완전 일치는 실제 AI 모드에서도 API 호출을 생략한다.

## API

모든 경로는 `/api` 기준이다. POST는 `application/json`, 브라우저 식별은 기존 `X-OneFix-Client-Id` 규약을 사용한다.

| 메서드 | 경로 | 내용 |
|---|---|---|
| GET | `/questions` | 참여 인원순 전체 대표 요청과 개인 참여 여부 |
| POST | `/questions` | `requestId`, `clientId` UUID, `department`, `period`, `title`, `description` 접수 |
| GET | `/questions/:id` | 공통 답변을 포함한 대표 요청 |
| POST | `/questions/:id/participations` | `clientId`로 중복 없는 참여 |
| GET | `/admin/questions` | 담당자 목록 |
| GET | `/admin/questions/:id` | 대표 요청과 취합 원문 |
| PATCH | `/admin/questions/:id` | `answer`, 마지막 조회의 `updatedAt`으로 공통 답변 게시·수정 |

접수 응답은 `{question, merged, dedupMethod}`다. 같은 requestId/내용을 재전송하면 최초 결과를 반환하고 내용 변경은 409로 거절한다. 답변 수정 충돌도 409다. 같은 부서·시기의 접수는 프로세스 내에서 순차 처리하고 DB 저장만 짧은 트랜잭션으로 수행한다.

## 저장 및 운영 범위

`docs/questions-schema.sql`의 questions, question_submissions, question_participations를 기존 SQLite에 추가한다. 시설 테이블과 데이터는 변경하지 않는다. 참여 유일 키는 `(question_id, client_id)`다. 원문에는 내부 브라우저 ID를 노출하지 않는다.

관리자 로그인과 서버 API 권한 검사를 적용했다. 공개 원문·답변에는 개인정보를 입력하지 않는다. 운영 설정은 [Vercel 배포 가이드](deployment.md)를 따른다. 원문에는 개인정보를 입력하지 않도록 안내한다. 여러 기관 격리, AI 오병합 수동 분리, 알림 발송, 문의량 예측은 이번 구현 범위에 포함하지 않는다. 기존 시설 예측은 유지한다.

## 원문별 답변 추천과 개별 게시

공개 상세 API에도 모든 취합 원문과 게시된 개별 답변을 제공한다. 내부 요청 ID, payload hash, 브라우저 식별자는 노출하지 않는다. 각 원문을 펼치면 개별 검토 대기 / 추가 확인 요청 / 개별 답변 등록 상태를 확인한다. 공통 안내가 있다고 개별 원문의 해결을 뜻하지 않는다.

담당자는 각 원문의 `AI 추천 생성`을 눌러 초안을 받는다. 모델에는 해당 원문, 부서, 적용 시기, 등록된 공통 안내만 전달한다. 다른 사람의 원문이나 개별 답변은 전달하지 않는다. 출력은 answer, status, reason, missingInfo다. 근거가 없거나 추가 정보가 있으면 서버도 needs_clarification 상태를 강제한다. 미확인 일정·자격·개인 결과를 단정하지 않도록 지시하며 최종 사실 확인은 담당자가 수행한다.

추천은 자동으로 게시하거나 기존 작성 내용을 덮어쓰지 않는다. `이 초안으로 답변 작성` 후 수정하여 게시한다. 직접 작성도 가능하다. 공통 안내 변경 또는 개별 답변 버전 충돌 시 409를 반환하여 오래된 답변 덮어쓰기를 막는다. 기존 공통 안내와 참여 랭킹은 바뀌지 않는다. 개별 답변은 공개 답변이며 개인별 비공개 전송이 아니다.

| 메서드 | 경로 (/api 기준) | 내용 |
|---|---|---|
| GET | `/questions/:id` | 대표 요청 + 원문 + 게시된 개별 답변 (초안 제외) |
| POST | `/admin/questions/:id/submissions/:submissionId/suggestion` | 원문별 AI 추천 생성. 본문 불필요 |
| PATCH | `/admin/questions/:id/submissions/:submissionId` | `answer`, `status` (answered/needs_clarification), `revision`, `sourceUpdatedAt`으로 개별 답변 게시 |

추천 응답 `{suggestion: {answer,status,reason,missingInfo,mode,sourceUpdatedAt}}`의 sourceUpdatedAt은 공통 안내를 조회한 버전이다. 직접 작성 시 대표 요청 updatedAt을 사용한다. revision은 원문의 answerRevision (미게시 0)이다. 추천 실패는 503이며 작성 내용은 유지한다. mock 모드에는 AI와 구분된 확인 요청 템플릿을 반환한다.

question_submission_answers 테이블을 추가하며 기존 원문을 수정하지 않는다. 게시된 답변은 원문당 하나이며 수정 시 revision을 증가시킨다. 추천 초안은 저장하지 않으므로 새로고침 시 사라진다. 이 MVP에는 비공개 후속 대화, 원문 수정, 오병합 분리는 포함하지 않는다.
