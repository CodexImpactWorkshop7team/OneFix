# 제품·화면 명세

스펙 v1 · 2026-09-04 · 목표: 2명, 3시간의 로컬 웹 MVP.

## 사용 환경과 범위

시설 3개가 있는 학교 건물 한 곳을 가정한다. 사용자는 로그인 없이 QR로 접근한다. 관리자는 로컬 데모 화면에서 직접 처리 상태를 바꾼다. 담당자 계정·자동 배정·서비스 공개 운영은 포함하지 않는다.

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| F01 | 시설별 고정 URL과 QR, 현재 미해결 고장 조회 | P0 |
| F02 | 같은 고장에 참여, 브라우저 기준 중복 집계 방지 | P0 |
| F03 | 증상·설명으로 신고, 접수 결과 확인 | P0 |
| F04 | 같은 시설의 미해결 고장과 AI 중복 판별 | P0 |
| F05 | 관리자 영향 인원 정렬, 상태·예상 처리 변경 | P0 |
| F06 | 사진 1장 첨부·조회 | P1 |
| F07 | 시설별 다음 7일 예상 신고량 | P1 |
| F08 | 반복 고장 주의도와 근거 표시 | P1 |

AI 수리 진단, 채팅, 지도, 회원가입, 알림, 사진 AI 분석, 수동 병합·병합 취소, 시설 관리 화면, 실시간 업데이트는 제외한다.

## 용어와 수치

- **시설:** QR 하나가 가리키는 물리적 대상. 예: 프린터 A.
- **고장(Issue):** 관리자가 처리하는 문제 단위. 시설 하나에 여러 고장이 있을 수 있다.
- **신고(Report):** 사용자가 제출한 원문과 선택 사진. 병합해도 원문을 남긴다.
- **참여(Participation):** 한 고장에 불편을 겪는다는 표시. 최초 신고자도 자동 참여한다.
- **영향 인원:** 고장별 고유 `clientId` 수. 여러 고장의 인원을 합해 건물 전체의 고유 인원이라고 표현하지 않는다.
- **예상 신고량:** 같은 시설·날짜·사용자의 중복 제출을 제외한 신고 수를 기반으로 계산한다. 단순 참여는 포함하지 않는다.
- **반복 고장 주의도:** 최근 신규 고장 이력으로 판단하는 점검 참고값. 실제 고장 확률이 아니다.

## 화면 1 — 시설 목록 `/`

시설명, 위치, 미해결 건수, 시설 바로가기와 해당 URL의 QR을 표시한다. 별도 검색·페이지네이션은 없다. `관리자 데모` 링크를 제공한다.

QR의 값은 서버 설정 `APP_BASE_URL + /facilities/{id}`이며 시설 ID는 시드 초기화 후에도 바뀌지 않는다. localhost QR을 휴대폰에서 접속 가능한 것처럼 안내하지 않는다.

## 화면 2 — 시설 상세 `/facilities/[id]`

위에서부터 시설명·위치, 새로고침 버튼, 미해결 고장 카드, `다른 문제 신고` 버튼, 최근 해결 내역 최대 3건을 표시한다.

각 카드에는 증상, 대표 설명, 영향 인원, 상태, 예상 처리 문구, 최초 접수 시각과 `나도 겪고 있어요`를 표시한다. 미해결은 영향 인원 내림차순 → 접수 시각 오름차순 → ID 오름차순이다.

| 상태 | 화면 동작 |
| --- | --- |
| 불러오는 중 | 로딩 표시, 참여 버튼 비활성 |
| 미해결 없음 | `현재 접수된 고장이 없습니다` + `고장 신고하기` |
| 참여 전 | `나도 겪고 있어요` 활성 |
| 참여 요청 중 | 중복 클릭 차단, `반영 중…` |
| 참여 완료 | 서버 인원으로 갱신, `참여했어요` 비활성 |
| 조회·참여 실패 | 오류 문구와 재시도, 인원은 임의 증가시키지 않음 |
| 조회 후 이미 해결됨 | 참여 API의 409를 안내하고 다시 조회 |
| 존재하지 않는 시설 | 404 화면 + 시설 목록 링크 |

예상 처리 `null`은 `예상 처리 미정`이다. `acknowledged` 이상은 `담당자 확인 완료`로 설명할 수 있지만 담당자 이름을 만들지 않는다. 해결 내역에는 참여 버튼이 없다.

## 화면 3 — 신고 `/facilities/[id]/report`

시설명은 읽기 전용. 증상 선택, 설명 입력, P1 사진 입력, 접수 버튼을 제공한다.

| 항목 | 검증·동작 |
| --- | --- |
| 증상 | `not_working` 작동 안 됨 / `poor_performance` 성능 이상 / `physical_damage` 외관·부품 파손 / `leak_or_noise` 누수·소음 / `other` 기타 중 하나 |
| 설명 | 앞뒤 공백 제거 후 5–500자, 필수. JS 문자열 길이 기준으로 서버·클라이언트 동일 검사 |
| 사진 | 선택, JPEG/PNG/WebP 1장, 최대 5MiB(5,242,880바이트), 미리보기·제거 |
| 접수 중 | 입력·버튼 비활성, `기존 신고를 확인하고 있어요…` |
| 접수 실패 | 입력을 유지하고 같은 `requestId`로 재시도. 내용 수정 시 새 ID 발급 |
| 접수 성공 | 새 고장 또는 병합 안내, 현재 영향 인원, `시설 상태로 돌아가기` |

사진 기능이 꺼져 있으면 사진 입력 자체를 숨긴다. 파일 오류를 조용히 무시해 사진 없이 접수하지 않는다. `AI 확인이 지연되어 별도 신고로 접수했어요`는 접수 성공 안내이며 실패 화면이 아니다.

## 화면 4 — 관리자 `/admin`

상단에 미해결 고장 수, 처리 중 건수, 해결 건수를 표시한다. 기본 목록은 미해결이며 `해결됨` 탭으로 전환할 수 있다. 해결 목록은 해결 시각 내림차순 → ID 오름차순이다.

고장 행에 시설명·위치·증상·영향 인원·상태·예상 처리 문구를 표시한다. 행을 펼치면 연결된 신고 원문·사진과 상태 수정 폼이 나온다. 별도 상세 페이지는 만들지 않는다.

- 상태와 예상 처리를 편집한 후 `저장`으로 한 번에 반영한다.
- 저장 성공 후 서버 응답으로 행을 갱신하고 목록을 다시 조회한다.
- 해결된 고장은 미해결 목록에서 빠진다. 실패 시 수정 입력을 유지한다.
- 사진은 관리자 상세에서만 보여주고 사용자 시설 페이지에는 원문 사진 전체를 노출하지 않는다.
- P1 예방 점검 영역은 기존 수리 목록 아래에 둔다. 예측 수치로 현재 영향 인원 정렬을 바꾸지 않는다.
- 예측에는 기준일·관측기간·근거·데모 여부를 함께 표시한다. 실패·기능 꺼짐·데이터 부족을 각각 구분한다.

## 상태 전이

```text
reported(접수됨) → acknowledged(확인됨) → in_progress(처리 중) → resolved(해결됨)
```

현재 상태 유지와 위 방향으로 건너뛰기는 허용한다. 예: 접수 직후 해결 가능. 역방향·재열기는 409다. `resolved`는 최종 상태이며 같은 증상이 재발하면 새 고장이다.

해결할 때 `resolvedAt`을 서버 시각으로 기록하고 `etaText`를 null로 비운다. 해결 상태를 반복 저장해도 최초 `resolvedAt`을 유지한다. 예상 처리는 자유 문구 1–80자 또는 null이며 공백만 있으면 null로 정규화한다.

## 익명 사용자·공통 UX

`localStorage.onefix.clientId`에 UUID를 저장한다. API를 보내는 시점에 초기화하고 서버 렌더링 중에는 접근하지 않는다. 저장소를 사용할 수 없으면 탭 메모리에서 ID를 유지하고 새로고침 시 중복 방지가 제한됨을 안내한다. 이는 계정 인증이 아니다.

360px 모바일과 1280px 데스크톱에서 가로 넘침 없이 사용한다. 주요 터치 버튼은 44px 이상, 입력마다 레이블, 오류는 텍스트로 연결한다. 상태는 색상만으로 구분하지 않는다. 날짜는 `Asia/Seoul`로 표시하고 새로고침 시 최신 값을 확인한다.

기본 UI의 빨강은 미해결 표시이며 안전 위험도 판정이 아니다. 관리자 처리 상태와 예방 점검 주의도는 서로 다른 배지로 표시한다.
