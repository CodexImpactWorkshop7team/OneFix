# OneFix — 같은 고장, 하나의 신고

> 시설 QR로 처리 현황을 확인하고, 같은 고장 신고를 모아 수리와 예방 점검의 우선순위를 정하는 서비스.

학교·기숙사·회사에서 같은 고장을 여러 사람이 따로 신고하는 문제를 해결한다. 사용자는 기존 신고에 참여하고, 관리자는 **영향 인원·처리 상태·반복 고장 이력**을 한곳에서 확인한다.

**진행 조건:** Codex 워크샵 · 2인 1조 · 맥북 1대에서 역할 구분 없이 함께 진행 · 개발 180분.

**현재 상태:** 로컬에서 실행 가능한 MVP. 시설 조회·QR·신고·참여·관리자 처리·사진 첨부·예측 카드를 구현했다. API 키 없이 바로 실행되며, 기본 병합 방식은 화면에 표시되는 **데모 규칙 모드**다. OpenAI 연결 코드는 포함되어 있지만 실제 API 호출은 키가 없어 확인하지 않았다.

## 바로 실행

Node.js 22.13 이상이 필요하며 이 맥북에서는 26.7.0을 사용한다.

```sh
npm ci
npm run dev
```

[시설 현황](http://localhost:3000) · [관리자 화면](http://localhost:3000/admin)

DB가 없으면 첫 요청 때 시설 3개와 합성 신고 이력을 자동으로 준비한다. 신고는 `data/onefix.sqlite`, 사진은 `data/uploads/`에 저장하며 재시작해도 유지된다. 별도 DB 서버는 필요 없다.

실제 AI 병합을 사용하려면 `.env.example`을 `.env.local`로 복사하고 `DEDUP_MODE=openai`, `OPENAI_API_KEY`, `OPENAI_MODEL`을 설정한 뒤 서버를 재시작한다. 모델은 계정에서 사용 가능한 구조화 출력 지원 모델을 지정한다. 키·모델 설정이 없거나 호출이 실패하면 신고는 별도로 접수되고 중복 확인 실패 안내가 표시된다.

데모 데이터를 처음 상태로 되돌리려면 개발 서버를 중지한 뒤 실행한다. **기존 로컬 신고·사진이 삭제된다.**

```sh
npm run db:seed:demo -- --reset
npm run dev
```

데모 이력 없이 시설만 준비하려면 새 DB 경로를 지정해 `npm run db:seed`를 먼저 실행한다. CLI 시드 명령은 셸 환경 변수를 사용한다. 휴대폰 QR 접속은 `.env.local`의 APP_BASE_URL을 맥북의 접속 가능한 LAN 주소로 설정한다. 관리자 인증은 없는 로컬 워크샵용이다.

## 구현·확인 범위

- F01–F08의 시설 화면, 접수·참여, 병합, 관리자 처리, 사진 첨부, 이력 기반 예측을 구현했다.
- API 핵심 흐름을 한 번 확인했다: 신고 → 동일 신고 병합 → 반복 참여 인원 유지 → 해결 처리 → 사용자 재조회.
- 합성 데이터의 예상 신고량은 프린터 7건, 에어컨 2건, 정수기 데이터 부족으로 계산됐다.
- 실제 OpenAI 호출·휴대폰 QR 스캔·사진 업로드의 별도 시연은 미확인이다. 전체 테스트·lint·build·브라우저 QA는 실행하지 않았다.

## 제품 흐름

```text
시설 QR → 현재 고장 확인 ┬→ 같은 문제에 참여 → 영향 인원 증가
                        └→ 새 신고 → AI 중복 판별 → 기존 고장 병합 / 새 고장

관리자 → 영향 인원 순 처리 목록 → 상태·예상 처리 변경 → 사용자에게 공유
       └→ 예방 점검 → 반복 고장 주의도 + 다음 7일 예상 신고량
```

AI는 **증상 문장으로 중복을 판별하는 일**만 맡는다. 사진은 증빙으로 첨부한다. 추가 예측 기능의 첫 버전은 신고 이력을 집계하는 규칙·통계 방식으로 만들고, 실제 고장 확률이나 고장 시점을 단정하지 않는다.

## 구현 우선순위

| 단계 | 기능 | 완료 기준 |
| --- | --- | --- |
| P0 · 필수 | 시설 QR·상태 조회, 참여, 신고, 문장 AI 병합, 관리자 처리 | 구현됨. 실제 AI는 키·모델 설정 필요 |
| P1 · 추가 | 사진 1장, 신고량 예상·반복 고장 주의도 카드 | 구현됨. 사진·예측 기본 활성화 |
| P2 · 이후 | 사진 AI 병합, 실제 고장 예측 모델, 알림, 인증·다중 조직 | 워크샵 이후 별도 진행 |

예측은 학습 모델이 아닌 이력 기반 계산이다. 상세 문서의 180분 계획은 워크샵 진행 기준으로 유지한다.

## 한 맥북에서 진행하는 방식

하나의 작업 폴더와 개발 서버에서 기능 단위로 순서대로 구현한다. 팀원별 역할·파일 소유·별도 개발 브랜치를 나누지 않는다.

첫 15분에 실행 환경과 공통 타입을 준비하고, 각 기능의 데이터·API·화면을 연결한 뒤 다음 기능으로 넘어간다. 두 브라우저 프로필로 사용자와 관리자를 시연한다. 상세 작업 순서·인수 조건은 [실행 계획](docs/delivery.md)을 따른다.

불필요한 QA·테스트 추가·반복 검증은 하지 않는다. 문서 수정은 변경 내용 확인으로 마무리하고, 코드 수정은 해당 기능에 필요한 최소 확인만 수행한다. 전체 테스트·타입 검사·lint·build를 매번 일괄 실행하지 않는다.

## 예측 기능의 모습

```text
예방 점검 · 데모 데이터 기반

프린터 A                 반복 고장 주의도: 높음
최근 30일 신규 고장 3건  ·  현재 미해결 1건
다음 7일 예상 신고: 약 7건
근거: 지난 4주 신고 28건 ÷ 4

최근 반복 이력이 있어 예방 점검을 권장합니다.
고장 확률이 아닌 이력 기반 참고 지표입니다.
```

신고량은 같은 사용자의 같은 시설·같은 날짜 신고를 한 번만 세며, 참여 버튼 클릭 수와 구분한다. 숫자·주의도는 임의 생성하지 않고 명세의 계산 결과를 표시한다. 데이터가 부족하면 예상 수치 대신 `데이터 부족`을 표시한다.

## 개발 시작 순서

1. 제품·API 명세와 작업 순서를 함께 확인한다.
2. Next.js + TypeScript + Tailwind CSS 프로젝트와 SQLite를 초기화하고 버전·lockfile을 고정한다.
3. 공통 타입·시드·환경 변수 예시를 추가한다.
4. 조회 → 참여·신고 → AI 병합 → 관리자 → P1 순으로 각 기능의 API와 화면을 연결한다.
5. [완료 조건](docs/delivery.md)의 핵심 흐름을 한 번 확인하고 3분 데모를 준비한다.

로컬 워크샵 시연을 목표로 한다. 실제 실행은 위의 `바로 실행`을 따르고, 세부 구조는 [개발 환경 문서](docs/architecture.md)를 참고한다.
