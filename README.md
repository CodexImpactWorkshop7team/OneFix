# OneFix — 같은 고장, 하나의 신고

> 시설 QR로 고장과 처리 현황을 확인하고, 같은 문제를 겪는 사람들을 하나의 신고로 모으는 서비스.

Codex 워크샵에서 **2인 1조, 3시간** 안에 만드는 웹 MVP 기획서다. 아래 기능과 기술 구성은 구현 목표이며, 아직 구현된 상태는 아니다.

## 1. 해결하려는 문제

학교·기숙사·회사에서는 같은 시설 고장을 여러 사람이 따로 신고한다. 사용자는 이미 접수됐는지 몰라 다시 신고하고, 관리자는 흩어진 신고를 확인하느라 실제로 몇 명이 불편한지 파악하기 어렵다.

OneFix는 **시설별 QR → 기존 고장 확인 → 같은 문제에 참여 → 처리 현황 공유**로 이 중복을 줄인다. AI는 새 신고가 기존 고장과 같은지 판단하는 좁은 역할만 맡는다.

- **사용자:** 고장 여부와 처리 현황을 빠르게 확인하고, 같은 문제라면 다시 설명하지 않고 참여한다.
- **관리자:** 고장별 영향 인원과 처리 상태를 한곳에서 보고 우선순위를 정한다.
- **첫 사용 환경:** 학교 건물 한 곳. 프린터 A, 307호 에어컨, 1층 정수기 3개 시설로 시연한다.

## 2. 3시간 뒤 보여줄 결과

사용자가 프린터 A의 QR을 찍으면 다음 정보를 확인한다.

```text
프린터 A · 도서관 1층

🔴 출력되지 않음
8명이 같은 문제를 겪고 있어요
담당자 확인 완료 · 예상 처리: 오늘 18:00

[나도 겪고 있어요]  [다른 문제 신고]
```

같은 문제가 보이면 `나도 겪고 있어요`를 누른다. 다른 문제라면 증상을 선택하고 설명과 사진을 제출한다. 설명이 기존 신고와 같다고 AI가 판단하면 기존 고장에 합쳐지고, 다른 문제라면 별도 고장으로 등록된다.

관리자 화면은 **미해결 고장을 영향 인원 내림차순**으로 보여준다. 인원이 같으면 먼저 접수된 고장을 위에 둔다. 관리자가 처리 상태와 예상 처리 문구를 바꾸면 사용자는 새로고침으로 이를 확인한다.

## 3. MVP 범위

| 기능 | 이번에 구현할 범위 |
| --- | --- |
| 시설 QR | 미리 등록한 시설 3개의 상세 페이지로 연결되는 QR |
| 시설 상세 | 위치, 미해결 고장 목록, 영향 인원, 처리 상태, 예상 처리 문구 |
| 기존 고장 참여 | `나도 겪고 있어요` 버튼과 중복 클릭 방지 |
| 새 신고 | 증상 선택 + 짧은 설명 필수, 사진 1장 선택 첨부 |
| 중복 판별 | 같은 시설의 미해결 고장에 한해 AI로 설명을 비교 |
| 관리자 목록 | 미해결 고장 우선순위 정렬, 해결된 고장은 별도 영역 |
| 관리자 수정 | `접수됨 → 확인됨 → 처리 중 → 해결됨`, 예상 처리 문구 입력 |
| 데모 데이터 | 시설 3개와 고장·참여자 샘플 데이터, 초기화 스크립트 |

**이번에 제외:** 회원가입, 실제 담당자 배정, 알림·문자, 다중 조직, 시설 등록 화면, 지도, 실시간 동기화, 사진 기반 AI 분석, 관리자 간 협업, 자동 수리 진단.

관리자 화면은 로컬 워크샵 시연용으로 인증 없이 만든다. 공개 운영은 MVP 범위에 포함하지 않는다.

## 4. 핵심 규칙

### 신고와 영향 인원

- **신고(Report)**는 사용자가 보낸 원문·사진이고, **고장(Issue)**은 여러 신고가 모이는 관리 단위다. 병합해도 원본 신고는 보존한다.
- 한 시설에 여러 고장이 동시에 존재할 수 있다. `출력 안 됨`과 `용지함 파손`을 무조건 하나로 합치지 않는다.
- 영향 인원은 신고 개수가 아니라 **해당 고장에 참여한 고유 사용자 수**다. 최초 신고자도 1명으로 센다.
- 로그인 대신 브라우저에 저장한 익명 `clientId`를 사용한다. 같은 고장에 재참여하거나 재신고해도 인원은 한 번만 증가한다.
- 이는 브라우저 기준의 데모 수치다. 다른 기기나 브라우저까지 동일인으로 식별하지는 않는다.
- 해결된 고장은 중복 판별 대상에서 제외한다. 같은 증상이 다시 발생하면 새 고장으로 접수한다.
- 미해결 고장이 없으면 `현재 접수된 고장이 없습니다`로 표시한다. 실제 정상 작동을 보증하는 표현은 쓰지 않는다.

### AI 중복 판별

1. 서버가 **같은 시설 + 미해결 상태**의 고장만 후보로 조회한다.
2. 후보가 없으면 AI 호출 없이 새 고장을 만든다.
3. 후보의 증상·대표 설명과 새 신고의 증상·설명을 AI에 전달한다. 사진은 증빙으로 저장하며 AI에 보내지 않는다.
4. AI는 구조화된 결과 `{"duplicateIssueId": "issue_1"}` 또는 `{"duplicateIssueId": null}`을 반환한다. 애매한 경우에는 `null`을 반환하도록 지시한다.
5. 서버가 반환된 ID가 실제 후보에 포함되는지 검증한 뒤 병합한다. 병합 시 기존 고장에 신고와 참여자를 연결한다.
6. 타임아웃·API 오류·잘못된 응답이면 새 고장으로 저장한다. AI 실패로 신고 접수가 막히지 않도록 한다.
7. 사용자에게 `기존 고장 신고에 합쳐졌어요` 또는 `새 고장이 접수됐어요`와 연결된 고장을 보여준다.

AI의 성공 기준은 문장을 생성하는 능력이 아니라 **같은 고장은 합치고 다른 고장은 구분하는 것**이다. 관리자 수동 병합·병합 취소는 후속 과제로 둔다.

## 5. 화면과 기술 구성

별도 모바일 앱 없이 모바일 화면에 맞춘 웹으로 만든다. 팀에 기존 템플릿이 없다면 **Next.js + TypeScript + Tailwind CSS**, 서버 데이터는 **SQLite**, AI는 **서버에서 OpenAI API 호출**로 구성한다. 별도 백엔드 프로젝트나 외부 인증 서비스는 두지 않는다.

| 경로 | 화면 |
| --- | --- |
| `/` | 데모 시설 3개, 각 시설의 QR과 바로가기 |
| `/facilities/[id]` | 시설 정보, 고장 목록, 참여 버튼 |
| `/facilities/[id]/report` | 새 신고 폼과 접수 결과 |
| `/admin` | 고장 우선순위 목록, 상태·예상 처리 수정 |

- 사진은 최대 5MB의 JPEG/PNG/WebP 1장으로 제한하고 로컬 업로드 디렉터리에 저장한다.
- API 키는 서버 환경 변수에만 둔다. 브라우저에 전달하지 않는다.
- QR의 주소는 `APP_BASE_URL`로 만든다. 휴대폰 시연 시 같은 Wi-Fi에서 접근 가능한 개발 서버 주소를 사용하고 실제 접속을 확인한다.
- 네트워크 연결이 안 되면 발표용 브라우저에서 시설 바로가기로 동일 흐름을 시연한다. 배포는 필수 완료 조건이 아니다.

### 두 사람이 먼저 합의할 데이터 구조

| 데이터 | 최소 필드 |
| --- | --- |
| Facility | `id`, `name`, `location` |
| Issue | `id`, `facilityId`, `symptom`, `description`, `status`, `etaText`, `createdAt` |
| Report | `id`, `issueId`, `clientId`, `description`, `photoUrl?`, `createdAt` |
| Participation | `issueId`, `clientId`, `createdAt` — `(issueId, clientId)` 유일 제약 |

상태 값은 `reported`, `acknowledged`, `in_progress`, `resolved`로 고정한다. 영향 인원 `affectedCount`는 Participation에서 계산한다. 새 고장 생성 또는 병합과 참여자 추가는 하나의 트랜잭션으로 처리한다.

### API 계약

| 메서드·경로 | 입력 | 핵심 응답 |
| --- | --- | --- |
| `GET /api/facilities/:id` | 시설 ID | `{ facility, issues }` |
| `POST /api/issues/:id/participations` | `{ clientId }` | `{ affectedCount, alreadyParticipated }` |
| `POST /api/reports` | multipart: `facilityId`, `clientId`, `symptom`, `description`, `photo?` | `{ issueId, merged, affectedCount }` |
| `GET /api/admin/issues` | 없음 | `{ issues }` — 시설 정보 포함, 우선순위 정렬 |
| `PATCH /api/issues/:id` | `{ status, etaText }` | `{ issue }` |

목록의 Issue에는 `affectedCount`를 포함한다. 오류 응답은 `{ error: { code, message } }`로 통일한다. 시설 목록은 공통 데모 데이터 파일을 사용한다.

## 6. 2인 역할 분담

실제 팀원 이름이 정해지면 A/B를 바꿔 적는다. 첫 15분에 API 응답 예시까지 고정하고, 이후 각자의 담당 파일을 중심으로 작업한다.

| 담당 | 팀원 A — 사용자 경험·화면 | 팀원 B — 데이터·AI·서버 |
| --- | --- | --- |
| 책임 | 사용자가 QR에서 접수까지 막힘없이 진행 | 신고 저장, 중복 병합, 관리자 변경이 일관되게 동작 |
| 구현 | 시설·신고·관리자 화면, QR 생성, 사진 입력, 로딩·오류·완료 표시 | DB·시드, API 전체, 사진 저장, AI 판별, 정렬·중복 참여 방지 |
| 주 담당 파일 | `src/app/**/page.tsx`, `src/components/**`, 스타일 | `src/app/api/**`, `src/lib/server/**`, DB·시드 스크립트 |
| 첫 산출물 | 공통 응답 예시로 동작하는 화면과 API 호출 연결부 | 타입에 맞는 API와 시드 데이터 |
| 시연 역할 | 사용자 신고·참여 흐름 진행 | 관리자 상태 변경, AI 병합 근거와 구조 설명 |

**공통 파일 담당:** B가 프로젝트 초기화·패키지 설치·공통 타입(`src/types/domain.ts`)·데모 데이터를 만들고 A에게 전달한다. A는 초기화 동안 화면 흐름과 문구를 정리한다. 이후 패키지나 공통 타입 변경은 상대에게 먼저 알린다.

Codex에는 `이 API 계약에 맞춰 시설 상세와 신고 폼 구현` 또는 `이 규칙에 맞춰 신고 저장과 중복 판별 구현`처럼 담당 범위와 완료 조건을 함께 전달한다. 각자 수정 파일을 제한하고, 30분마다 실행 상태와 계약 변경 여부를 공유한다.

## 7. 180분 실행 계획

| 시간 | 팀원 A | 팀원 B | 확인할 결과 |
| --- | --- | --- | --- |
| 0–15분 | 화면 흐름·문구 확정 | 프로젝트 초기화, API 키 확인, 타입·데이터 확정 | 함께 실행 가능, API 계약 합의 |
| 15–55분 | 시설 상세·신고 폼·참여 UI | DB·시드·조회·참여·신고 API | AI 없이 새 신고 저장과 조회 가능 |
| 55–95분 | API 연결, 관리자 화면 구현 | AI 중복 판별, 사진 저장, 관리자 API | 같은 문제 병합·다른 문제 분리 가능 |
| 95–125분 | 관리자 API 연결, 모바일 화면·QR | 영향 인원·정렬·오류 처리 점검 | 사용자와 관리자 전체 흐름 연결 |
| 125–155분 | 실제 시나리오 실행, 화면 결함 수정 | 데이터·AI·중복 참여 결함 수정 | 아래 필수 검증 통과 |
| 155–180분 | 발표 화면·진행 연습 | 시드 초기화, 서버·QR 접속 점검 | 기능 추가 중단, 3분 데모 완주 |

**시간이 부족할 때 줄이는 순서:** 사진 첨부 → QR 표시 화면 꾸미기 → 관리자 디자인. 신고·참여·상태 변경·문장 기반 중복 판별을 먼저 완성한다. QR은 화면 디자인을 생략해도 시설 링크에 대한 이미지로 준비한다.

API 키나 네트워크 문제가 해결되지 않으면 규칙 기반 시연 모드로 흐름을 검증하고 화면에 `데모 판별 모드`를 표시한다. 이 경우 실제 AI 중복 판별은 미완료로 명시한다.

## 8. 완료 조건과 필수 검증

- [ ] 시설 QR 또는 바로가기로 해당 시설의 현재 신고 상태를 확인한다.
- [ ] 첫 신고를 제출하면 고장 1건이 생성되고 영향 인원이 1명이 된다.
- [ ] 다른 브라우저의 사용자가 참여하면 인원이 1명 증가한다.
- [ ] 같은 브라우저에서 반복 참여·재신고해도 같은 고장의 인원은 늘지 않는다.
- [ ] `출력 버튼을 눌러도 종이가 안 나와요`와 `인쇄를 보내도 출력이 안 됩니다`가 하나의 고장으로 합쳐진다.
- [ ] 같은 프린터의 `용지함 손잡이가 부러졌어요`는 별도 고장으로 등록된다.
- [ ] 다른 시설의 신고와 해결된 고장은 병합 대상에 포함되지 않는다.
- [ ] 관리자가 상태·예상 처리 문구를 수정하면 시설 화면 새로고침 후 반영된다.
- [ ] 관리자 목록에서 영향 인원이 큰 미해결 고장이 먼저 표시된다.
- [ ] AI 호출이 실패해도 새 신고가 저장되고 사용자에게 접수 결과를 보여준다.
- [ ] 서버 재시작 후에도 저장된 신고와 상태가 유지된다.

## 9. 발표용 3분 데모

1. **0:00–0:20 — 문제:** “같은 프린터 고장을 여덟 명이 따로 신고하면, 관리자는 여덟 건을 읽어야 합니다.”
2. **0:20–0:50 — QR과 참여:** 프린터 QR을 열어 기존 고장을 확인하고, 새 사용자가 참여해 8명에서 9명으로 증가하는 모습을 보여준다.
3. **0:50–1:30 — AI 병합:** 다른 브라우저에서 같은 증상을 다른 문장으로 신고한다. 새 고장 카드가 생기지 않고 기존 고장에 합쳐져 10명이 되는 것을 보여준다.
4. **1:30–2:00 — 구분:** 같은 프린터의 용지함 파손을 신고해 별도 고장 카드가 생기는 것을 보여준다.
5. **2:00–2:40 — 관리자:** 영향 인원 순 목록을 보여주고 프린터 고장을 `처리 중`, 예상 처리를 `오늘 18:00`으로 변경한다.
