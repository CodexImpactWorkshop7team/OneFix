# OneFix — 요청은 한곳에서, 관리는 로그인 후

시설 불편과 행정 요청을 같은 웹에서 접수하고, 관리자가 처리 현황과 답변을 공유합니다.

- 방문자: `/requests`에서 로그인 없이 시설·행정 요청 등록
- 관리자: `/login` → `/admin`에서 처리·답변·AI 추천 관리
- 로컬 실행: `npm ci` → `npm run admin:setup` → `npm run dev`
- 관리자 로그인 정보: `.admin-credentials.txt` (Git 제외)
- **Vercel 배포**: [배포 가이드](docs/deployment.md). Turso DB와 관리자 환경 변수 등록 필요

사진은 최대 1MB이며 새 첨부 파일은 DB에 저장합니다. 아래 초기 기획 문서보다 위 운영 안내와 배포 가이드가 우선합니다.

# OneFix — 같은 고장, 하나의 신고

> 시설 QR로 처리 현황을 확인하고, 같은 고장 신고를 모아 수리와 예방 점검의 우선순위를 정하는 서비스.

학교·기숙사·회사에서 같은 고장을 여러 사람이 따로 신고하는 문제를 해결한다. 사용자는 기존 신고에 참여하고, 관리자는 **영향 인원·처리 상태·반복 고장 이력**을 한곳에서 확인한다.

**진행 조건:** Codex 워크샵 · 2인 1조 · 맥북 1대에서 역할 구분 없이 함께 진행 · 개발 180분.

**현재 상태:** 로컬에서 실행 가능한 MVP. 시설 조회·QR·신고·참여·관리자 처리·사진 첨부·예측 카드를 구현했다. API 키 없이 실행하면 기본 병합 방식은 **데모 규칙 모드**다. 이 맥북은 로컬 환경 설정으로 실제 OpenAI 모드에 연결했으며, `gpt-4.1-mini`로 중복 신고 병합을 한 번 확인했다. 키와 로컬 환경 설정은 Git에 포함하지 않는다.

## 바로 실행

Node.js 22.13 이상이 필요하며 이 맥북에서는 26.7.0을 사용한다.

```sh
npm ci
npm run dev
```

[시설 현황](http://localhost:3000) · [관리자 화면](http://localhost:3000/admin)

DB가 없으면 첫 요청 때 시설 3개와 합성 신고 이력을 자동으로 준비한다. 신고는 `data/onefix.sqlite`, 사진은 `data/uploads/`에 저장하며 재시작해도 유지된다. 별도 DB 서버는 필요 없다.

실제 AI 병합을 사용하려면 `.env.example`을 `.env.local`로 복사하고 `DEDUP_MODE=openai`, `OPENAI_API_KEY`, `OPENAI_MODEL`을 설정한 뒤 서버를 재시작한다. 모델은 계정에서 사용 가능한 구조화 출력 지원 모델을 지정한다. 키·모델 설정이 없거나 호출이 실패하면 신고는 별도로 접수되고 중복 확인 실패 안내가 표시된다.

데모 데이터를 처음 상태로 되돌리려면 개발 서버를 중지한 뒤 실행한다. **기존 로컬 신고·사진이 삭제된다.**

```sh
npm run db:seed:demo -- --reset
npm run dev
```

데모 이력 없이 시설만 준비하려면 새 DB 경로를 지정해 `npm run db:seed`를 먼저 실행한다. CLI 시드 명령은 셸 환경 변수를 사용한다. 휴대폰 QR 접속은 `.env.local`의 APP_BASE_URL을 맥북의 접속 가능한 LAN 주소로 설정한다. 관리자 인증은 없는 로컬 워크샵용이다.

## 구현·확인 범위

- F01–F08의 시설 화면, 접수·참여, 병합, 관리자 처리, 사진 첨부, 이력 기반 예측을 구현했다.
- API 핵심 흐름을 한 번 확인했다: 신고 → 동일 신고 병합 → 반복 참여 인원 유지 → 해결 처리 → 사용자 재조회.
- 합성 데이터의 예상 신고량은 프린터 7건, 에어컨 2건, 정수기 데이터 부족으로 계산됐다.
- 실제 OpenAI 호출은 `gpt-4.1-mini`로 한 번 확인했으며 HTTP 201, `dedupMethod=ai`, `merged=true`로 기존 신고에 연결됐다.
- 휴대폰 QR 스캔·사진 업로드의 별도 시연은 미확인이다. 전체 테스트·lint·build·브라우저 QA는 실행하지 않았다.

## 제품 흐름

```text
시설 QR → 현재 고장 확인 ┬→ 같은 문제에 참여 → 영향 인원 증가
                        └→ 새 신고 → AI 중복 판별 → 기존 고장 병합 / 새 고장

관리자 → 영향 인원 순 처리 목록 → 상태·예상 처리 변경 → 사용자에게 공유
       └→ 예방 점검 → 반복 고장 주의도 + 다음 7일 예상 신고량
```

AI는 **요청 중복 판별**과 **행정 요청의 원문별 답변 초안 추천**을 맡는다. 답변 게시 전 담당자 검토를 거친다. 사진은 증빙으로 첨부한다. 추가 예측 기능의 첫 버전은 신고 이력을 집계하는 규칙·통계 방식으로 만들고, 실제 고장 확률이나 고장 시점을 단정하지 않는다.

## 한 맥북에서 진행하는 방식

하나의 작업 폴더와 개발 서버에서 기능 단위로 순서대로 구현한다. 팀원별 역할·파일 소유·별도 개발 브랜치를 나누지 않는다.

첫 15분에 실행 환경과 공통 타입을 준비하고, 각 기능의 데이터·API·화면을 연결한 뒤 다음 기능으로 넘어간다. 두 브라우저 프로필로 사용자와 관리자를 시연한다. 상세 작업 순서·인수 조건은 [실행 계획](docs/delivery.md)을 따른다.

불필요한 QA·테스트 추가·반복 검증은 하지 않는다. 문서 수정은 변경 내용 확인으로 마무리하고, 코드 수정은 해당 기능에 필요한 최소 확인만 수행한다. 전체 테스트·타입 검사·lint·build를 매번 일괄 실행하지 않는다.

## 예측 기능의 모습

```text
예방 점검 · 데모 데이터 기반

프린터 A                 반복 고장 주의도: 높음
최근 30일 신규 고장 3건  ·  현재 미해결 1건
다음 7일 예상 신고: 약 7건
근거: 지난 4주 신고 28건 ÷ 4

최근 반복 이력이 있어 예방 점검을 권장합니다.
고장 확률이 아닌 이력 기반 참고 지표입니다.
```

신고량은 같은 사용자의 같은 시설·같은 날짜 신고를 한 번만 세며, 참여 버튼 클릭 수와 구분한다. 숫자·주의도는 임의 생성하지 않고 명세의 계산 결과를 표시한다. 데이터가 부족하면 예상 수치 대신 `데이터 부족`을 표시한다.

## 개발 시작 순서

1. 제품·API 명세와 작업 순서를 함께 확인한다.
2. Next.js + TypeScript + Tailwind CSS 프로젝트와 SQLite를 초기화하고 버전·lockfile을 고정한다.
3. 공통 타입·시드·환경 변수 예시를 추가한다.
4. 조회 → 참여·신고 → AI 병합 → 관리자 → P1 순으로 각 기능의 API와 화면을 연결한다.
5. [완료 조건](docs/delivery.md)의 핵심 흐름을 한 번 확인하고 3분 데모를 준비한다.

로컬 워크샵 시연을 목표로 한다. 실제 실행은 위의 `바로 실행`을 따르고, 세부 구조는 [개발 환경 문서](docs/architecture.md)를 참고한다.

## 시설을 넘어 행정 요청까지

OneFix의 상위 용어는 **요청**입니다. 시설 요청은 고장과 불편을, 행정 요청은 기관·사무국·캠퍼스의 궁금증을 모읍니다. 사용자가 같은 요청에 참여하면 담당자는 우선순위를 파악하고 한 번의 처리 안내나 공통 답변을 공유합니다.

- **시설 요청**: 기존 QR → 시설 상태 → 중복 취합 → 처리 현황 흐름을 유지합니다.
- **행정 요청**: `/questions`에서 부서·적용 시기·제목·내용을 입력합니다. 같은 답변으로 해결할 수 있는 요청을 취합하고 ‘나도 궁금해요’ 인원순으로 보여줍니다.
- **행정 요청 관리**: `/admin/questions`에서 취합된 원문을 확인하고 공통 답변을 게시·수정합니다. 답변 완료 목록은 검색 가능한 FAQ로 사용할 수 있습니다.
- 같은 부서와 적용 시기의 최근 30개 대표 요청만 AI 병합 후보로 사용합니다. 자격·기간·대상이 다르거나 모호하면 별도로 접수합니다. AI는 원문별 답변 초안도 추천하며, 담당자가 검토·수정한 내용만 게시합니다.
- 기존 답변이 있는 요청에 취합되면 해당 답변을 바로 확인합니다. 답변 알림 발송은 없으며 게시판 새로고침으로 최신 내용을 확인합니다.
- 작성과 참여를 합쳐 요청별 브라우저당 1명으로 집계합니다. 같은 사람이 재작성해도 랭킹 인원은 늘지 않습니다.
- 새 테이블은 첫 행정 요청 API 접근 때 추가됩니다. 기존 시설·신고 데이터는 유지됩니다. 별도 데이터 초기화가 필요 없습니다.

상세 범위와 API는 [행정 요청 스펙](docs/questions.md)을 참고하세요. 기존 문서의 ‘신고’와 ‘질문’은 각각 시설 요청과 행정 요청을 뜻하며, API 경로와 DB 이름은 호환성을 위해 유지합니다.

### 원문별 답변 추천

취합된 요청의 제목 또는 **원문 N건 보기**를 누르면 각 원문과 게시된 개별 답변을 펼칠 수 있습니다. 담당자 화면에서는 원문별 **AI 추천 생성 → 초안으로 답변 작성 → 검토한 개별 답변 게시** 순서로 진행합니다.

- 원문과 등록된 공통 안내를 바탕으로 답변 초안, 추천 이유, 확인할 정보를 제공합니다.
- 공통 안내가 없거나 조건이 불명확하면 추가 확인을 요청합니다. 신청 자격·일정·개인 심사 결과를 임의로 확정하지 않도록 구성했습니다.
- AI 추천 자체는 게시되지 않습니다. 담당자가 `개별 답변 등록` 또는 `추가 확인 요청`으로 게시합니다.
- 원문과 개별 답변은 공개 게시판에 표시됩니다. 비공개 메시지 기능이 아니므로 개인 식별정보를 넣지 않습니다.
- 추천은 버튼을 누를 때만 생성하고 화면 안에 임시 보관합니다. 게시한 답변은 SQLite에 저장합니다.

## 시연 데이터 추가

`npm run db:demo:add`로 기존 데이터를 지우지 않고 시설 6개, 시설 요청 18건, 행정 요청 16묶음과 원문 46건을 추가합니다. 공통 안내·개별 답변·추가 확인 요청과 참여 인원 랭킹을 포함합니다. 같은 명령을 다시 실행해도 중복 추가하거나 기존 답변을 덮어쓰지 않습니다.

Vercel에서는 `SEED_DEMO_DATA=true` 환경 변수를 등록하면 최초 DB 접근 때 같은 예시를 한 번 추가합니다. 예시 제목·시설명과 상단 배너로 시연 데이터임을 표시합니다. 실제 서비스 운영 시에는 이 옵션을 끄세요. 이미 추가된 예시는 옵션을 꺼도 자동 삭제되지 않습니다.
